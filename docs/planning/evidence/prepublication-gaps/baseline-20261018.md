### Second review before source — findings and disposition

- Version selection was underspecified: npm update respects existing constraints;
  Cargo update updates the lock selection without silently turning into cargo add;
  pip only-if-needed requires retained installed-state constraints. Added these
  semantics and failure tests instead of assuming a command alias is sufficient.
- Existing npm transaction and PyPI owned-distribution replacement/rollback were
  already implemented. Identified verifyManagedOrEmpty and prepare/commit/rollback
  for reuse; an unmanaged developer project is a separate read-only adoption gap.
- Terraform's current explicit-reference argument is not native project-wide
  init -upgrade. GitHub has no universal native update command. Marked their actual
  selection/ownership gaps instead of promising automatic argument forwarding.
- Direct Host process invocation from CLI would violate responsibility placement.
  Put only presentation selection in CLI, the fixed read-only provider in existing
  hosttool and callback composition in bootstrap. No new generic executor/Port.
- Windows system files do not satisfy Unix-root ownership semantics on DrvFS;
  do not weaken artifact tool identity to accept them. Fixed standard system-path
  display probe and unavailable fallback are documented separately.
- Repeated configure/pre-run/help can multiply OS processes and a saved-auto
  confirmation can become stale. Added per-command probe caching and immediate
  effective-source output; keep persisted auto unchanged.
- OS fallback can hide a failed probe; require stable selection-source/reason
  output. Bound subprocess output/time/pipe wait, prohibit profiles/module
  autoload and arbitrary PATH, and distinguish actual WSL success, fixture tests,
  cross-compile and future native macOS CI evidence.
- The previous private source projection omitted a bootstrap regression. All new
  untracked implementation/tests/docs must be included in one explicit inventory
  before checks/build; compare final staged hashes against that inventory.

and [WSL Windows interoperability](https://learn.microsoft.com/en-us/windows/wsl/filesystems#run-windows-tools-from-linux)

mechanisms, not an implemented or qualified Go/WSL bridge. Remote VS Code terminals
run on their execution host; a remote server's preferences are not the local
