## Implementation order — only the missing scope

1. Preserve native build, runtime lock, signing identity and installer interfaces.
   Add a narrow release package command with bounded regular-file inputs,
   exclusive outputs, explicit version/source timestamp and fixed Linux amd64
   payload roles. Do not expand dynamic OS/architecture support.
2. Use a pinned Go packaging library through `go.mod`/`go.sum`, not a floating
   PATH tool or a new externally installed packaging CLI. nFPM's
   [documented library API](https://nfpm.goreleaser.com/docs/quick-start/#using-as-a-go-library)
   supports both formats. Its exact
   [v2.47.0 module](https://github.com/goreleaser/nfpm/blob/v2.47.0/go.mod)
   requires Go1.26.4; the existing repository-selected Go1.26.9 is sufficient.
   Keep the existing five managed quality tools and runtime compiler owner intact.
   Acquire only the exact reviewed module with checksum verification; no `latest`.
3. Add package records to the existing manifest producer. Let the canonical
   manifest own the exact candidate set; derive checksum, attestation and publish
   consumer lists from it. Validate safe basenames, regular files, unique records,
   role/platform/source bindings, digest and size before consuming names.
4. Test actual `.deb`/`.rpm` bytes, native payload digests, version/architecture,
   owner/mode, fixed timestamp and reproducibility. Exercise unsafe paths,
   symlink/pre-existing output, malformed metadata and payload mismatch. Do not
   install on or alter the active workstation to run package tests.
5. Run canonical Quick/security/workflow/release-gate and focused package/manifest/
   installer regressions on the complete candidate. Any dependency addition also
   needs the canonical vulnerability check. Reuse native preparation conventions;
   source/check success is not publication authority.

This is extension of the existing manifest/workflow consumers, not a replacement
of an IMPLEMENTED feature. If inspection proves replacement necessary, stop and
present the existing location, reason, alternatives and impact before seeking
approval as required by AGENTS.md.
